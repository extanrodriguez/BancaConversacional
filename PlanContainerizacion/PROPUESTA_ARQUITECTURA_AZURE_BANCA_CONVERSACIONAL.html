1. Resumen ejecutivo

Este documento consolida tres fuentes:

  • Estado operativo actual — VM vm-test002-genesis con systemd, Python 3.12, Azure OpenAI y deploy manual por ZIP/SSH.
  • Plan interno del repositorio — PlanContainerizacion/ con fases 1–3 (Docker → Container Apps → Producción).
  • Propuesta externa — arquitectura microservicios con Container Apps, Redis, APIM, AI Gateway e integración DataPower/ACE/Core.
Veredicto: Para Banca Conversacional Genesis, la opción recomendada es Azure Container Apps (ACA) como plataforma de ejecución en Azure, evolucionando desde el baseline VM actual mediante el roadmap ya definido en el repo. AKS queda reservado para cuando exista un requisito corporativo explícito de plataforma Kubernetes, cargas muy grandes/sostenidas o portabilidad on-premise con OpenShift. Azure App Service no es la opción óptima para este caso por limitaciones en microservicios, sesión distribuida y control de contenedores.

Conclusión comparativa: Para Genesis en su etapa actual, Container Apps gana en costo, simplicidad y time-to-market. AKS gana en completitud de plataforma y control. La propuesta correcta no es "ACA o AKS", sino ACA ahora + imágenes Docker portables + contratos desacoplados, dejando AKS como evolución cuando el banco lo exija.

6.1 Interpretación de costos

  • Más barato en plataforma: Container Apps (~USD 55–120/mes lab) vs AKS (~USD 400–800/mes mínimo con 3 nodos).
  • VM actual es competitiva en costo fijo, pero no escala y tiene mayor costo operativo humano (patching, deploy manual, monitoreo).
  • App Service parece barato pero no soporta bien el patrón conversacional multi-réplica con Redis, MCP sidecar y evolución a microservicios.
  • Coste real del LLM puede superar toda la infraestructura: optimizar fast-path (ya implementado) reduce tokens y es la palanca económica principal.
Nota: Los costos de producción bancaria incluirán APIM + App Gateway + Redis Standard/Premium + multi-AZ. Presupuesto producción estimado: USD 800–2,500/mes (plataforma) + tokens OpenAI según volumen.

7.2 Respuestas directas

¿Container Apps o AKS para banca conversacional?

Container Apps para la fase actual y producción MVP. AKS cuando el banco requiera Kubernetes corporativo o portabilidad on-premise.

¿Cuál es más barata?

Container Apps (~3–5× menos costo de plataforma que AKS mínimo). VM es similar en compute pero más cara en operación.

¿Cuál es más completa?

AKS ofrece control total de Kubernetes, networking, policies y portabilidad. Container Apps es más completa que VM para escala cloud-native.

¿App Service?

No recomendado para este caso. Mejor para web apps simples, no para orquestación conversacional multi-componente.

12. API de Contexto — Primera carga (incluye CDT / Certificados)

El API de contexto es la primera carga al iniciar sesión. Debe traer el portafolio del cliente suficiente para personalizar, desambiguar productos y responder consultas de lectura frecuentes sin otra llamada al Core. No debe incluir movimientos, historial ni datos transaccionales.

Principio: Catálogo de productos activos + snapshot de lectura por tipo. Los CDT (Certificados de Depósito a Término) se identifican en Core como categoría CD y en la cognitiva como TERM_DEPOSIT.

12.4 CDT / Certificados (CD → TERM_DEPOSIT)

Los CDT deben venir en la primera carga con los campos específicos del Excel. La cognitiva responde preguntas como: "¿Cuánto tengo en mi certificado?", "¿Cuándo vence mi depósito a plazo?", "¿Cuál es la tasa de mi CDT?" mediante el intent TERM_DEPOSIT_DETAIL_READ.

Reglas de negocio CDT (primera carga)

  • Mostrar currentBalance / availableBalance como capital invertido.
  • Mostrar maturityDate como fecha de vencimiento del certificado.
  • Mostrar interestRateCd como tasa pactada e interestAmountCd como intereses acumulados.
  • Si el cliente tiene 2+ CDT (ej. uno DOP y uno USD), desambiguar por moneda o últimos 4 dígitos.
  • Señales conversacionales reconocidas: certificado, depósito, depósito a plazo, CDT, DAP, capitalización, modalidad, vencimiento, tasa.
  • Estado activo CD: productStatus 1 o 3 según tabla Core.

14. Conclusión

La propuesta externa de Container Apps es sólida y alineada con el plan interno del repositorio. El merge produce un camino claro:

  1. Mantener la VM 8447 como baseline operativo mientras se implementa Fase 1.
  2. Implementar Redis como prerrequisito no negociable para escala.
  3. Migrar a Container Apps (Fase 2) como plataforma Azure destino — más barata, más simple y suficiente para banca conversacional MVP/producción media.
  4. Reservar AKS para evolución enterprise o portabilidad on-premise, usando las mismas imágenes Docker.
  5. Descartar App Service para este workload específico.

La arquitectura de aplicación (guardrails, contratos, APIs, observabilidad) debe permanecer independiente de la plataforma de ejecución, permitiendo evolucionar de VM → Container Apps → AKS sin reescribir la lógica de negocio conversacional.

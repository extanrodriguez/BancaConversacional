1. Objetivo del sistema

Permitir que el cliente, desde el canal conversacional del banco, consulte información de sus productos (cuentas, tarjetas, préstamos) y conocimiento institucional (definiciones, requisitos, procesos), con respuestas en lenguaje natural, sin que el modelo invente saldos ni cambie de cliente.

En QA vigente, la capa cognitiva es lab8446 en el puerto 8447. El orquestador .NET permanece intocable: él obtiene el portafolio Core y lo entrega a la cognitiva, que lo persiste en Redis.

2. Actores

3. Casos de uso funcionales

CU-01 · Cargar contexto de cliente (WRITE PATH)

Disparador: apertura de sesión o refresco de portafolio.

  1. El orquestador obtiene el portafolio autenticado desde Core / Presentation Product.
  2. Invoca POST /turn con context_info=true, question=null, customer_id, conversation_id y context.data.
  3. La cognitiva valida el payload y persiste en Redis: session:{conv}, customer:{id}:snapshot, customer:{id}:portfolio.
  4. Responde CONTEXT_LOADED o CONTEXT_REFRESHED con genesis_write=true.

Resultado: la conversación queda autenticada y con portafolio en Redis. Sin LLM.

CU-02 · Consultar / comparar productos propios (READ PATH)

Ejemplo: «compara Full Car vs Joven», «¿cuál es mi disponible?».

  1. El orquestador envía POST /turn con la misma conversation_id y question.
  2. Azure OpenAI decide tool-calling hacia get_customer_products.
  3. El tool lee customer:{id}:portfolio en Redis (no inventa datos).
  4. El modelo redacta la respuesta solo con evidencia del tool.
  5. Se devuelve VALID_CONTRACT con reply / app_channel.

CU-03 · Conocimiento institucional

Ejemplo: misión del banco, requisitos de un producto genérico.

  1. La pregunta no requiere datos personales del portafolio.
  2. Se consulta FAQ local y/o Foundry + AI Search.
  3. La respuesta no afirma saldos ni productos concretos del cliente.

CU-04 · Health / readiness operativo

  • GET /health — liveness del servicio lab8446.
  • GET /ready — Redis alcanzable (Entra MI) y servicio listo.

5. Reglas de negocio

  1. No inventar cifras. Saldo, disponible, tasa, cuota y fechas salen del portafolio Redis o se declara que no están disponibles.
  2. No cambiar de cliente. El customer_id lo fija la sesión autenticada; el modelo no puede sustituirlo.
  3. Separación de fuentes. Datos personales → Redis/tools. Conocimiento genérico → FAQ/Foundry/Search.
  4. Orquestador dueño del Core. La cognitiva no reconstruye el portafolio desde Core en cada pregunta de producto.
  5. Misma conversación. WRITE y READ comparten conversation_id.
  6. Fail-closed Redis. Si Redis no está listo, /ready falla; no se opera en memoria en QA promovido.

Plan HITL: Backoffice de curación RAG

Visión de producto (no implementada): un backoffice donde el usuario funcional gestiona tickets con criticidad, cura respuestas que alimentan Azure AI Search / Foundry, entrena por prompts con rollback, consulta la base de conocimiento, ve estadísticas en tiempo real y —a futuro— el log de la banca conversacional. Principio: capturar ≠ aprender; nada llega al modelo sin aprobación humana versionada.

1. Visión: dónde se genera y dónde se resuelve

Respuesta directa: el ticket se genera automáticamente en Cognitiva (detección en /turn). El funcional le da seguimiento y lo resuelve dentro del backoffice HITL — una interfaz web interna (no la APK del cliente).
QuéDóndeQuién
Señal de error / feedback Chat APK o UI /pruebas Cliente / tester
Creación del ticket + criticidad API Cognitiva → store (DB/Redis) del backoffice Sistema
Seguimiento y resolución Backoffice HITL (web interna con SSO/Entra ID) Usuario funcional
Publicación al “modelo” Azure AI Search (bsc-kb-conocimiento) + instrucciones agente Foundry + overrides de Q→A Backoffice dispara pipeline tras aprobación

Nota técnica: no se “reentrena” el LLM base (fine-tune) en caliente. Se actualiza el contexto recuperable (RAG / agent instructions / reglas canónicas). Eso es lo que hace que “cuando pregunten X, responda lo que indicó el funcional”.

3. Tickets: generación, criticidad y resolución en plataforma

Cómo se crea el ticket

  1. Cliente envía feedback en el chat.
  2. Detector (regex + LLM) clasifica y sugiere criticidad.
  3. Cognitiva persiste el ticket y notifica al backoffice (badge + opcional Teams/correo).
  4. Cliente recibe ack; la KB no cambia todavía.

Grados de criticidad

NivelCriterioSLA sugerido
P0 — Crítica Dato incorrecto de producto/tasa/requisito; riesgo compliance; respuesta ofensiva o con fuga técnica (citas, dumps). ≤ 4 h laborables
P1 — Alta Enrutamiento malo (Redis vs KB), clarificación innecesaria repetida, respuesta incompleta frecuente. ≤ 1 día laboral
P2 — Media Tono/UX, redacción, casos edge poco frecuentes. ≤ 3 días
P3 — Baja Mejora opcional, falso positivo, elogio con sugerencia. Backlog

El funcional puede subir/bajar criticidad al abrir el ticket.

Resolver directamente en el backoffice

  1. Abrir ticket → ver pregunta, respuesta IA, feedback, tool, conversation_id (sin PII sensible en claro si se enmascara).
  2. Clasificar tipo: contenido KB / routing / tono / personal (no-RAG) / falso positivo.
  3. Escribir respuesta canónica y variantes de pregunta (incl. typos).
  4. Elegir destino de publicación:
    • qa_override — regla Q→A de alta prioridad (parche rápido),
    • search_chunk — documento/chunk en bsc-kb-conocimiento,
    • foundry_instruction — instrucción del agente KB,
    • router_rule — preferir Redis vs Search.
  5. Preview + smoke en QA → Publicar → estado published → verificar → verified.

4. Cómo se “actualiza el modelo Azure AI”

Mecanismo recomendado: cuando el funcional publica una curación, el backoffice escribe/actualiza el contexto en Azure (Search + Foundry), no hace fine-tune del LLM. En el siguiente turno, si la pregunta hace match con lo registrado, el recuperador / agente usa ese contexto y responde lo indicado.
Acción del funcionalEfecto en Azure / Cognitiva
Alta de Q→A canónica Documento/override indexado en AI Search (campo prioridad alta). Foundry/Search lo recupera primero.
Edición de chunk KB Update + reindex parcial del índice bsc-kb-conocimiento.
Prompt / instrucción Nueva versión de instrucciones del agente Foundry genesis-kb-agent-poc (o capa de system overlay versionada).
Regla de router Config/regla en Cognitiva (no Azure model weights): forzar tool Redis o KB.

Flujo deseado: «cuando pregunten X o Y (registradas en backoffice) → responder lo que indicó el funcional» = match semántico/exacto sobre overrides curados + retrieval del chunk aprobado.

5. ¿Se puede ver y actualizar la base de conocimiento en el backoffice?

Sí. El backoffice debe ofrecer un explorador del índice Azure AI Search (bsc-kb-conocimiento): listar, buscar, previsualizar chunks, editar, crear, desactivar y publicar con versionado. Es la forma correcta de “ver lo que sabe el modelo” en un sistema RAG.

Capacidades KB en backoffice

  • Ver: búsqueda full-text / filtros por producto, tema, fuente, fecha de publish.
  • Leer detalle: texto del chunk, metadatos, embeddings status, documentos vinculados.
  • Actualizar: editar texto → diff → aprobación → reindex → smoke de 1–3 preguntas ancla.
  • Crear: nuevo FAQ / glosario / política desde plantilla.
  • Desactivar / rollback: soft-delete o restaurar versión anterior.
  • No mostrar: secretos, keys, ni datos personales de clientes en la KB pública.

Lo que no se “ve” como KB: saldos y fechas personales viven en Redis/Core, no en Search. El backoffice puede enlazar a “dato personal → no curar en RAG” y abrir ticket de routing.

6. Entrenamiento por prompts directos + plan de rollback

El funcional puede enviar prompts / instrucciones que se aplican al agente Foundry (o a una capa de “system overlay” de Cognitiva) sin tocar el chat del cliente.

Flujo

  1. Redactar instrucción en el módulo “Entrenamiento” (ej. «Si preguntan misión del banco, responder exactamente…»).
  2. Validación automática (longitud, prohibido PII, tono).
  3. Guardar como prompt_version = N+1 en estado draft.
  4. Smoke en QA con 5 utterances de prueba.
  5. Publicar a QA → luego a prod (doble gate si funcional_admin).
  6. Queda registrada la versión anterior como rollback inmediato.

Plan de rollback

DisparadorAcción
Funcional pulsa “Revertir” Restaurar prompt_version = N-1 (o versión marcada “última estable”).
Smoke post-publish falla Auto-rollback a versión estable + ticket P0.
Spike de feedback negativo (stats) Alerta + opción de rollback con un clic.
Auditoría / compliance Historial inmutable: autor, diff, timestamp, entorno.
Guardrail: un prompt no debe contradecir políticas del banco ni inventar tasas. El copiloto de curación marca riesgo high y exige doble aprobación.

12. Sugerencias adicionales

  1. Overrides Q→A de alta prioridad antes que reescribir documentos largos: cura rápida y medible; luego consolidar en la KB “oficial”.
  2. Ambientes separados: publish siempre a QA primero; prod solo con rol admin + smoke verde.
  3. No fine-tune del LLM en caliente: más costo, menos control y peor rollback. Preferir RAG + instrucciones versionadas.
  4. Separar tickets “dato personal” (Redis/Core) de tickets “conocimiento”: evita envenenar la KB con datos de un cliente.
  5. Prueba de regresión ancla: suite fija (misión, fecha de corte glosario, Visa Platinum…) que corre tras cada publish.
  6. Deduplicar tickets: agrupar por embedding de la pregunta para no inundar la cola con el mismo error 50 veces; subir criticidad al cluster.
  7. Cuatro-ojos en P0: un funcional cura, otro aprueba si hay impacto regulatorio.
  8. Telemetría de “cite noise” y hedges como KPIs de calidad (ya hubo incidentes de dumps de citas).
  9. Enlace ticket ↔ chunk: desde el ticket, saltar al fragmento KB que se usó (si hay citation limpia interna).
  10. Modo “solo lectura” para auditoría del banco sin poder publicar.

13. Prompts de operación

13.1 Detector de feedback (sistema)

Eres el detector de feedback de Banca Conversacional (Banco Santa Cruz).
Clasifica el ÚLTIMO mensaje del cliente respecto a la respuesta previa de la IA.

Entrada: question_prev, answer_prev, message_now, tool_used

Clases: negative_feedback | correction | do_not_ask | praise | not_feedback
Criticidad sugerida: P0 | P1 | P2 | P3
  P0 = dato falso / compliance / fuga técnica
  P1 = routing o respuesta incompleta recurrente
  P2 = tono/UX
  P3 = menor / dudoso

Si hay duda → not_feedback y suggested_queue=false.
No inventes hechos. No propongas cambios al índice.
JSON:
{
  "is_feedback": true|false,
  "class": "...",
  "severity": "P0|P1|P2|P3",
  "confidence": 0.0-1.0,
  "summary": "una frase",
  "suggested_queue": true|false
}

13.2 Copiloto de curación (backoffice)

Eres copiloto de curación HITL en el backoffice de Banco Santa Cruz.
El funcional decide; tú propones.

Salida JSON:
diagnosis, canonical_answer, question_variants[3+],
publish_target: qa_override|search_chunk|foundry_instruction|router_rule|n/a,
knowledge_patch|n/a, foundry_instruction_patch|n/a, router_note|n/a,
test_utterances[3], risk: low|medium|high, rollback_hint

Reglas:
- Sin tasas ni fechas personales inventadas
- Portafolio del cliente → no va a KB (router_note → Redis)
- Sin citas 【n:m†source】 ni dumps numéricos
- Español, tono banca

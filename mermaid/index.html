Cuándo hay modelo

En casi todo READ salvo chitchat. Azure elige tool; Foundry/Search atienden conocimiento (incl. typos).

Cuándo hay banco

El orquestador arma context.data desde Core. La cognitiva no reconstruye el portafolio en cada pregunta.

Cuándo hay Foundry

Cuando Azure elige search_bank_knowledge. Saldos personales solo vía Redis.

5. Cómo decide la cognitiva (intención)

Gate local mínimo: solo saludo/chitchat. El resto lo decide Azure OpenAI eligiendo entre las dos tools. El hint de semantic_intent es red de seguridad si el LLM no llama tool. Azure AI Search resuelve typos al recuperar documentos.

6. Artefactos internos (qué hace cada uno)

Runtime en /opt/genesis-cognitive-8447/lab8446_runtime (código fuente hermano: BancaConversacional8446/lab8446/). El sibling Genesis aporta el WRITE PATH Redis y el cliente Foundry KB.

app.py — FastAPI

lab8446/app.py

Expone el contrato HTTP. Enruta context_info al WRITE PATH y el resto a LabConversationalAgent.run_turn. Formatea la respuesta al envelope del orquestador (VALID_CONTRACT, app_channel).

  • Endpoints: /turn, /health, /ready, UI /pruebas/
  • No interpreta intención: delega en el agente

semantic_intent.py — Hint / chitchat

lab8446/semantic_intent.py

Gate local de chitchat + hint de seguridad si Azure no llama tool. Ya no es el router principal KB vs Redis.

  • Chitchat → suggested_tool=none
  • Hint products vs RAG solo como fallback

agent.py — Orquestación del turno

lab8446/agent.py

Chitchat local; resto → Azure OpenAI con tool_choice=auto. Ejecuta la tool elegida (Redis o Foundry/Search).

  • Debug: router, azure_chose_tools
  • Si Foundry responde final=true, se usa esa respuesta
  • Sin tool → safety con hint local

kb_search.py — Conocimiento

lab8446/kb_search.py

Camino preferido: agente Foundry genesis-kb-agent-poc (mismo playground). Si la respuesta evade o falla, cae a Azure AI Search (bsc-kb-conocimiento) y, si hace falta, síntesis grounded.

  • No envía preguntas personales al agente KB
  • Evita expansión de query que contamine Search con «Banco Santa Cruz» genérico
  • Prefiere Foundry cuando la respuesta cubre el producto pedido

foundry_kb_agent.py — Cliente Foundry

sibling …/rag/foundry_kb_agent.py

Invoca el proyecto Foundry vía AIProjectClient / responses API. Flag GENESIS_FOUNDRY_KB_AGENT=1.

  • Agente: genesis-kb-agent-poc (versión en env, p.ej. 9)
  • Índice detrás: Azure AI Search del playground
  • Skip si el texto parece banca personal

tools.py — Schemas de tools

lab8446/tools.py

Schemas + system prompt: Azure debe elegir KB vs Redis; Search cubre typos; never inventar.

product_context_service.py — READ Redis

lab8446/product_context_service.py

Lee el portafolio de la sesión desde Redis. Filtra por tipo (ACCOUNT, LOAN, CREDIT_CARD, DEPOSIT) y campos pedibles (saldo, tasa, disponible…).

  • Fuente: customer:{id}:portfolio
  • Aislamiento por customer_id de la sesión autenticada

context_write.py — WRITE PATH

lab8446/context_write.py

Persiste context.data del orquestador. Reutiliza ContextPersistenceService del sibling Genesis (CAS session/snapshot) y sincroniza el portfolio lab para las tools.

  • Sin LLM
  • Meta UI en labmeta:{conv} para no pisar session:{id}
  • Respuesta: CONTEXT_LOADED, genesis_write=true

security_context.py — Identidad de turno

lab8446/security_context.py

Lleva customer_id, conversation_id y display_name del turno. Impide que el modelo “cambie de cliente”.

reply_format.py — Presentación

lab8446/reply_format.py

Normaliza el texto al cliente (markdown ligero, deduplicación de saludos). No altera la decisión semántica.

redis_store.py — Cliente Redis

7. Contrato del orquestador externo → cognitiva

El orquestador apunta a un solo endpoint de negocio: POST http://20.127.25.24:8447/turn. Healthchecks opcionales: /health, /ready.

ModoCampos claveEfecto en cognitiva
WRITE — cargar contexto context_info=true, question=null, customer_id, conversation_id, context_op (load|refresh), context.data Persiste en Redis. Sin LLM. Devuelve CONTEXT_LOADED.
READ — pregunta NL Misma conversation_id + question (o message) Chitchat local, o Azure elige tool → Redis / Foundry. Envelope VALID_CONTRACT + reply.

Qué no debe llamar el orquestador

/lab/login, /orch/context, /chat/front, /debug/* — solo UI/lab.

Validación de “tareas”

Azure elige tool; la evidencia (Redis o Search) valida la respuesta. Si falla la tool, se admite el miss sin inventar.

8. Plan — alimentar el RAG con feedback (NO implementado)

Objetivo: cuando el usuario diga cosas como «no me preguntes eso», «está mal» o corrija la respuesta, capturar el caso en un backoffice HITL donde el usuario funcional resuelve tickets por criticidad, cura Q→A hacia Azure Search/Foundry, entrena con prompts versionados (rollback), ve la KB y estadisticas. Documento: PLAN_FEEDBACK_RAG_HITL.html · PROMPT_FEEDBACK_RAG_HITL.md

Fases propuestas

FaseQué hace el sistemaQuién interviene
1. Detectar Clasificar feedback negativo / corrección / «no preguntes X» (regex + prompt detector). Solo el usuario final genera la señal.
2. Capturar Guardar pregunta previa, respuesta IA, feedback, tool, conversation_id, customer_id. Automático.
3. Acusar recibo «Gracias, lo registramos para mejorar» (sin cambiar la KB). Usuario final solo recibe confirmación.
4. Cola HITL Panel / cola feedback:pending. Usuario funcional abre la cola (fuera del chat del cliente).
5. Curar Copiloto (prompt B) propone; el funcional define respuesta/regla y destino (Search / Foundry / router). Intervención clave del usuario funcional — aquí se ajustan los errores.
6. Publicar Actualizar bsc-kb-conocimiento y/o instrucciones Foundry; reindexar. Funcional + ops aprueban el publish.
7. Verificar Smoke de la pregunta original (y typos). Usuario funcional / QA cierra el ticket.

Cómo entra el usuario funcional a corregir

  1. Recibe aviso de tickets pending_review.
  2. Abre el caso: pregunta, respuesta IA, feedback del cliente, tool usada.
  3. Clasifica (KB / routing Redis vs Search / tono / falso positivo).
  4. Ajusta: escribe la respuesta o regla correcta y el artefacto destino.
  5. Aprueba publicación → ops reindexa → funcional verifica smoke y cierra.

Datos personales (saldo, corte de mi tarjeta) no se aprenden en el RAG: se corrigen en Core/Redis.
